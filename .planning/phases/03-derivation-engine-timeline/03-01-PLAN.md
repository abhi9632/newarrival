Write `src/lib/derive.ts`. This is the engine. It is pure: no clock read, no storage, no network, no React, and **zero runtime imports**. It imports types only, with the `import type` form, from `./rules` and `./profile`. That is load bearing: the type only form is fully erased, which is what lets `scripts/check-engine.ts` load this module directly under Node's native type stripping with no bundler, no path alias and no JSON import attribute. A plain value import of either module would pull `src/data/rules.json` into the graph and break the check.

Export from it:

- `DUE_SOON_DAYS`, the integer 7, the window TIME-03 and TIME-05 both read.
- `type ObligationStatus`, the union `overdue`, `due-soon`, `upcoming`, `standing`. `standing` is the status of a rule with no single deadline, which is most of the corpus: the Phase 2 records use the `ongoing` anchor for standing conditions and only the arrival, course end and fixed anchors produce a date.
- `interface Obligation` carrying the flattened record fields the UI renders (`id`, `module`, `title`, `detail`, `agency`, `instrument`, `sourceUrl`, `verifiedOn`) plus `anchor`, `dueDate` as an ISO string or null, `status`, and `daysUntilDue` as an integer or null.
- `toUtcDays(iso)`: split the ISO string on the hyphen into three integers and return `Date.UTC(year, month - 1, day)` divided by 86400000. Never hand a string to the Date constructor and never use a local time getter. These are calendar dates, not timestamps, and a UTC parsed date read through local getters is the classic off by one that would put an obligation one day overdue on stage.
- `addDays(iso, n)`: build the result from `toUtcDays(iso) + n` multiplied back to milliseconds, then take the first ten characters of the ISO string. Because both operands are UTC midnights, the arithmetic is exact integer days and no daylight saving change can shift it.
- `applies(record, profile)`: true when every entry of `record.appliesTo` names a facet whose allowed value array contains the profile's value for that facet. An absent facet key means the record applies to every value of that facet; an empty object means it applies to everyone. Read the profile value through a single indexed access with one cast, because `appliesTo` keys are a subset of the `Profile` field names by the Phase 2 `applies-to` gate. This function contains no facet value literal and no per record special case. It is the whole of ENGINE-01.
- `dueDateFor(record, profile)`: returns `addDays` of the profile date field the anchor names plus `record.due.offsetDays` for the arrival and course end anchors, `record.due.date` for the fixed anchor, and null for the ongoing anchor. Express the anchor to profile field mapping as one small object literal. Anchor names and profile field names are not facet values, so they belong here.
- `statusFor(dueDate, today)`: null due date returns `standing`. Otherwise compute the integer day difference through `toUtcDays`; negative returns `overdue`, zero through `DUE_SOON_DAYS` inclusive returns `due-soon`, greater returns `upcoming`.
- `derive(records, profile, today)`: filter by `applies`, map to `Obligation` with the due date, status and day count filled in, then sort dated obligations ascending by `dueDate` followed by standing obligations in corpus order. ISO date strings compare lexicographically in chronological order, so sort on the strings and construct no Date objects here.

`today` is a parameter on `statusFor` and `derive`. It is never read from the system clock inside this module. If the engine read the clock, the demo would behave differently tomorrow than it did in rehearsal and every assertion would rot. The corpus arrives as the `records` parameter for the same reason: the engine is agnostic to which corpus it is given, which is what makes the check script able to run it against fixtures.

No literal from the locked matrix appears anywhere in this file. The four facet value sets are defined once, in `src/lib/rules.ts`, and this module never names one. No persona name from `docs/CONCEPT.md` appears either. The acceptance criteria enforce both with a negative grep, and Task 2 proves that grep can fail.

First edit `tsconfig.json`: add `"scripts"` to the `exclude` array. The check script imports its target with an explicit `.ts` extension, which is what Node's native type stripping requires and what `tsc` rejects unless `allowImportingTsExtensions` is set. Excluding the directory is the one line fix and it costs nothing, because these scripts are run by Node directly and never bundled.

Write `scripts/check-engine.ts`, plain Node with zero dependencies, using only `node:assert/strict`, `node:fs` and `node:url`. It reads the corpus with `readFileSync` and `JSON.parse` rather than importing it, which sidesteps JSON import attributes entirely. It takes an optional engine module path as `process.argv[2]`, defaulting to `src/lib/derive.ts`, resolves it to a file URL and loads it with a dynamic import. Every violation prints one stdout line shaped `FAIL <gate>: <what is wrong>`; on any violation it exits 1; on a clean run it prints `OK engine` and exits 0. Mirror `scripts/check-rules.mjs` exactly so there is one convention in the repo, not two.

Implement these nine named gates.

- `engine-01-source`. Read the target module file as text and assert it contains none of the six matrix facet values as a quoted literal and neither persona name from `docs/CONCEPT.md`. This is the gate that makes the pitch claim falsifiable rather than assertable: you cannot special case a profile's output without naming one of its facts.
- `engine-01-clock`. Assert the same file text contains no system clock read: no zero argument Date construction and no epoch millisecond static on the Date object. An injectable reference date is what keeps the demo reproducible and the assertions from rotting overnight.
- `engine-01-derive`. Derive both example profiles against a fixed reference date. Assert both sets are non empty, that each contains at least one obligation id the other lacks, and pin four ids from the Phase 2 corpus: the student work limit condition and the graduate visa window resolve for the student profile and not for the skilled one, and the sponsorship obligation and the permanent residence pathway resolve for the skilled profile and not for the student one. Then print one report line shaped `DIVERGENCE <symmetric difference count> of <union count>`; plan 03-03 consumes that number as evidence for the CONCEPT.md assumption test.
- `engine-02-dates`. For every dated obligation of the student profile, recompute the expected date independently inside the check from the anchor date and the record's `offsetDays`, and assert the engine agrees. Then assert three fixed boundary cases through `addDays`, chosen because each is a place a naive local time implementation goes wrong by one day: a span crossing the start of Australian daylight saving on 2026-10-04, a span crossing the year boundary from 2026-12-28, and a span landing on the leap day 2029 does not have, from 2028-02-27 forward two days to 2028-02-29.
- `engine-03-citizenship`. Derive the student profile, then derive it again with citizenship swapped and nothing else changed. Assert the symmetric difference of the two id sets is non empty and that every record in it has module `health`. This is ENGINE-03 as a property rather than an opinion, and it is the cleanest on stage proof that the engine is real.
- `engine-04-state`. The same shape with the state facet swapped and the symmetric difference required to be entirely module `tenancy`. If the corpus contains zero tenancy records, print `SKIP engine-04: no tenancy records in corpus, RULE-06 was cut` and do not fail. Cutting RULE-06 is item one of the binding cut order, so a skipped gate here is a planned outcome. Never delete the gate and never invent a record to make it fire.
- `time-03-status`. Assert the status boundary table against an injected reference date: one day before due is `overdue`, the due date itself is `due-soon`, exactly `DUE_SOON_DAYS` ahead is `due-soon`, one day past that window is `upcoming`, and a null due date is `standing`. Off by one at either edge of this table is exactly what a judge would notice.
- `engine-05-deterministic`. Call `derive` twice with identical arguments and assert the two results are deeply equal, then assert that changing one facet does change the result, so the determinism gate cannot be satisfied by a function that ignores its inputs.
- `time-01-order`. Walk the returned array and assert every dated obligation precedes every standing one and that the dated run is ascending by ISO date.

Name the persona in a comment inside the fixture so `engine-01-source` has something to find.
