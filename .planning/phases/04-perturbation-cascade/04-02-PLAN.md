<the_motion_spec>
The requirement is legibility, not richness. Three mechanical properties produce it and all three
are asserted:

1. **Stagger, capped.** Cards animate in order with a per card delay of
   `min(index, --cascade-max-steps) * --cascade-stagger`. The cap is what keeps a long timeline from
   turning a sub second event into a multi second one. Suggested values: stagger 40ms, max steps 10,
   duration 320ms, giving a worst case settle of 720ms.
2. **A bounded settle.** `(max-steps * stagger) + duration` must not exceed 900ms. Beyond that the
   judge stops reading it as one event and starts reading it as the page being slow.
3. **Motion that carries meaning.** A card that moved because its date moved animates its position.
   A card that changed status in place animates its colour and its marker, and does not move. A card
   that held does not animate at all. If everything animates identically, the motion carries no
   information and is decoration.

**Mechanism, in ladder order, no new dependency.**

- The per card change animation is plain CSS transitions on `transform`, `opacity`, `color` and
  `background-color`, driven by a delay set from the card index as an inline custom property. This
  is the baseline and it runs in every browser.
- The reorder, when a moved card changes its place in the date sorted list, is handled by
  `document.startViewTransition`, a platform API that does the position interpolation for free.
  Feature detect it. When it is absent the reorder snaps while the per card colour, marker and date
  transitions still stagger, so the pass still reads as one event on a browser that does not have it.
- No animation library. The project has held its dependency count at zero deliberately and the
  platform covers this.

**Reduced motion is a specified behaviour, not an absence.** A judge's machine may have
`prefers-reduced-motion: reduce` set, and a cascade that simply does not happen would read as a
broken demo. The required behaviour: the state still changes, every diff marker still renders,
every date and colour still updates, and the change is not animated. Concretely, `runCascade` skips
`startViewTransition` entirely and applies the state directly, and a
`@media (prefers-reduced-motion: reduce)` block in `globals.css` sets `--cascade-duration` and
`--cascade-stagger` to `0ms`. Both halves are required: the media query alone leaves the view
transition running, and the JavaScript branch alone leaves the CSS transitions running.

**No layout thrash.** Animate compositable properties only. Do not put a transition on a box model
property, because a staggered set of those forces a reflow per frame per card and the cascade
stutters on exactly the machine the demo runs on.
</the_motion_spec>

per frame per card and the cascade stutters on the demo machine, which is precisely the failure this

Nothing visitor facing changes in wording in this task. If a string does change, the dash rule and

<the_fallbacks>
Named in advance so the checkpoint has somewhere to go rather than stalling. Apply in order, in this
phase, and record which one was used.

1. **Fewer simultaneous movers.** Raise `--cascade-stagger` and lower `--cascade-max-steps` so the

   the pass runs so the cascade happens inside one screen height rather than partly below the fold.
   The cards that did not change are still there and still marked, they are just not competing for
   the eye during the sweep.

If all three are applied and the answer is still noise, record `FAIL` honestly with what was tried.
A recorded failure with three attempts behind it is a finding Phase 5 can act on. A `PASS` the
screenshot does not support is worse than either.
