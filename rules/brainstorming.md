# rules/brainstorming.md

Use this when a problem or feature needs exploring BEFORE implementation begins.

## When to invoke
- Broad problem brief ("we want to improve claims experience")
- Multiple valid solution directions exist
- Before committing to any architecture or UI pattern Day 1

## Process

### 1. Understand
- Ask one clarifying question at a time. Prefer multiple choice.
- "What problem does this solve for the user?"
- "Who is the primary user in this scenario?"
- "What does a successful demo look like to a judge?"
- Stop questioning when scope is clear.

### 2. Explore
- Present 2-3 approaches with trade-offs.
- Lead with the recommended option and explain why.
- Apply YAGNI ruthlessly: remove anything not needed for the demo.

### 3. Confirm and lock
- Get explicit approval on the chosen direction before writing any code.
- Write the agreed approach as a one-paragraph summary in HANDOFF.md Current state.

## Red flags
- Jumping to implementation without confirming direction
- Presenting only one option
- Designing beyond what the demo requires in 48 hours
