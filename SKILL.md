# SKILL: Hackathon Planning Automation
# Version: 6.4-hackathon -- general hackathon template
# Purpose: Feed GSD a structured problem brief so its questioning produces a focused
#          48-hour sprint plan, then fill AGENTS.md / CLAUDE.md / HANDOFF.md from
#          GSD's .planning/ artifacts once the plan is approved.
#          No client survey. No proposal builder. One planning session on Day 1 morning.

---

## GSD / SKILL DIVISION OF LABOUR

This contract defines what each system owns. Violating it wastes tokens and risks
contradicting GSD's output.

### GSD owns -- never redo these

| Concern | GSD artifact |
|---|---|
| Deep problem questioning | Interactive Q&A during `/gsd-new-project` |
| Domain + stack research | `.planning/research/STACK.md`, `FEATURES.md`, `ARCHITECTURE.md`, `PITFALLS.md` |
| Requirements scoping | `.planning/REQUIREMENTS.md` (feature list, demo-critical vs cut) |
| Time-boxed sprint roadmap | `.planning/ROADMAP.md` (phases, tasks, time estimates) |
| Project summary | `.planning/PROJECT.md` (problem, decisions, constraints) |
| Workflow config | `.planning/config.json` |
| Project state | `.planning/STATE.md` |
| Base workflow rules | Base `.claude/CLAUDE.md` (generated by GSD, merged not overwritten) |

### This skill owns -- GSD never produces these

| Concern | Skill artifact |
|---|---|
| Human-readable session context | `HANDOFF.md` (synthesised from `.planning/`) |
| Template governance rules | `CLAUDE.md` rules block (appended, never overwriting GSD's base) |
| Design system record | `design-system/README.md` |
| Agent execution spec | `AGENTS.md` (pages, routes, components, team ownership, tokens) |
| Session archive | `docs/session-archive.md` |

### Hard boundary rules

1. **GSD writes `.planning/`; this skill reads `.planning/`.** Data flows one way.
   Phase 3 never writes into `.planning/`.
2. **This skill never regenerates what GSD already generated.** No re-asking questions
   GSD asked. No re-summarising the roadmap. No rewriting CLAUDE.md from scratch. Additions only.
3. **Phase 3 is a single-pass read then write.** Read all required `.planning/` files
   once at the start of Phase 3, hold only the extracted fields in working memory, then
   produce all governance outputs in sequence. Do not re-read the same file in multiple steps.

## OVERARCHING GOAL

This is a 48-hour competition. Every decision is filtered through one question:
> Does this make the demo more compelling to a judge in the time remaining?

Quality and polish still matter -- judges notice. But completeness of features does not.
A tight, polished 3-screen flow beats a sprawling half-finished 10-screen app every time.

### NON-NEGOTIABLE WRITING RULE -- NO EM DASHES

Em dashes are banned across every file, every output, every commit message.
Use comma, colon, semicolon, parentheses, or split the sentence. No exceptions.

## HOW TO INVOKE

**Ideation Sprint runs first.** Before this skill runs, the lead runs `rules/ideation-sprint.md`
(a 90-minute concept lock) which writes `docs/CONCEPT.md`. This skill's planning input is
`docs/CONCEPT.md`, not the raw problem statement. If CONCEPT.md does not exist, stop and run
the Ideation Sprint first.

On Day 1 morning, once CONCEPT.md is locked:

- "Run the project planning skill. The brief is docs/CONCEPT.md plus DAY1.md EVENT CONFIG."

Claude executes ALL phases in sequence without further prompting.
Do NOT skip phases. Each phase gates the next.

**The flow:** Phase 1 reads the locked concept and locks constraints -> GSD questions the
team interactively, researches, scopes, and produces a roadmap -> Phase 3 fills
governance docs from GSD's output -> Phase 4 is the approval gate and execution start.

## HACKATHON CONSTRAINTS (hard limits fed to GSD)

These are non-negotiable. They go verbatim into the GSD brief doc in Phase 1.

**Time budget:**
- Day 1: problem brief received ~9am. Planning session: ~9am-10:30am max.
  First feature shipped by noon. Feature freeze: Day 2, 2 hours before demo.
- Day 2: morning polish only (no new features after feature freeze).
  Demo prep: 1 hour before presentation.

**Scope:**
- UI prototype only. No real backend. No database. No auth.
- All data is static JSON or hardcoded mock objects.
- Target: a working, clickable demo that tells a clear story from problem to solution.
- Judges do NOT test every edge case. They follow the happy path. Build that first.

**Stack:**
- Chosen on Day 1 morning. Fill into AGENTS.md immediately.
- Prefer what the team can ship fast in: React + Vite, Next.js, or plain HTML/CSS/JS.
- No new frameworks nobody on the team has used before.
- Deployment: Vercel or Netlify (1-click from repo). Must be live before demo.

**Judging rubric (feed to GSD as constraints):**

Read the rubric from DAY1.md EVENT CONFIG. Feed its criteria and weights to GSD as
constraints. Weight features by rubric points per hour of build time: the criterion worth
the most points earns the most build time. A simple, clear demo scores higher than a
complex one that is hard to follow.

Fallback rubric (use only when the event publishes none; recorded in EVENT CONFIG):

| Criterion | Weight | What judges look for |
|---|---|---|
| Problem clarity | equal | The problem is specific and immediately obvious |
| Solution quality | equal | The solution actually addresses the problem |
| UX polish | equal | The demo looks and feels designed, not templated |
| Feasibility | equal | The approach is realistic and the tech choice is explainable |
| Presentation | equal | The story is clear and easy to follow in about 3 minutes |

**UI polish:**
- Day 1, T1 only: run `frontend-design` and `design-taste-frontend` once to agree
  design tokens and fill `design-system/README.md`.
- Day 1 after T1: build features using those tokens. Do not re-run the full design pass.
- Day 2 after feature freeze: run the full visual polish pass.

## MULTI-DEVICE CONTINUITY

The repo is the only shared state between team members and between sessions.

1. **Pull before starting any feature.** Every session, every team member, every time.
   Git is the integration layer. Never assume another agent's work is in your local state.

2. **Commit and push after every completed component.** Not at end of day. After every
   component. In a 48-hour sprint, lost uncommitted work is unrecoverable.

3. **HANDOFF.md is the team's shared brain.** It tells any team member (or agent
   resuming on any device) exactly what is done, what is in progress, and what is next.
   Update it after every work block, not just end of session.

4. **Resuming mid-skill is automatic.** Before Phase 1, check `.planning/_intake/phase1-brief.md`
   and `.planning/ROADMAP.md`. If both exist, GSD already ran -- state "Resuming after
   GSD roadmap" and skip straight to Phase 3. If only the brief exists, invoke GSD now.
   Never restart from Phase 1 in a new session.

## PHASE 2: INVOKE GSD -- INTERACTIVE QUESTIONING + PLANNING

### Step 1 -- Run GSD interactively

Run `SlashCommand("/gsd-new-project @.planning/_intake/phase1-brief.md")`.

**Do NOT pass `--auto`.** Per GSD docs, `--auto` means: after the initial config
questions, skip the interactive interview and run research -> requirements -> roadmap
fully autonomously. That removes the multi-round Q&A where vague problem statements
get sharpened into precise scopes and feature priorities get cut to fit 48 hours.
The interview is the most valuable part of GSD for a hackathon. Keep it.

GSD will:
1. Ask the team its deep-question interview (scoping for a hackathon sprint)
2. Ask workflow preference questions -- answer with GSD's recommended defaults.
   Only surface a question to the team if it affects feature scope or team split.
3. Spawn parallel research subagents (stack, UX patterns, technical pitfalls)
4. Present a requirements list -- scope each item as: demo-critical / nice-to-have / cut
5. Produce `.planning/ROADMAP.md` as a time-boxed sprint plan (not a milestone plan)
6. Show the roadmap for approval, loop until the team approves

When GSD asks about roadmap granularity and execution mode, answer:
- Granularity: task-level (not epic-level -- tasks should be 1-2 hour chunks max)
- Execution: interactive (not automated -- team reviews each phase)
- Git tracking: yes
- Research agents: yes (but time-box the research -- this is a hackathon, not a startup)

**GSD's roadmap must respect the feature freeze deadline.** If GSD's generated
roadmap runs longer than the available build time (Day 1 noon to Day 2 feature freeze),
push back: "Scope this for [X] hours of build time. Cut or defer anything that does
not make the demo more compelling."

**Rubric gate -- verify before approving the roadmap:**

Before accepting GSD's roadmap, confirm every rubric criterion in DAY1.md EVENT CONFIG is
served by the plan. If any are missing, push back to GSD and request a revision before approving.

- For each rubric criterion: name at least one feature in the roadmap that serves it.
  If a criterion is unserved, ask GSD to add or reshape a task to cover it.

- Demo walkability: the roadmap must produce a demo happy path walkable in about 3 minutes.
  If the scope is too wide to demo cleanly, ask GSD to cut until it is.

- Iteration: the roadmap must include at least one explicit assumption-test checkpoint
  before feature freeze. If not, ask GSD to add one.

Do not approve the roadmap until every rubric criterion is served.

### Step 2 -- CLAUDE.md merge: append-only, never overwrite

GSD generates a CLAUDE.md. The existing CLAUDE.md in this repo is the source of truth.
Merge protocol:
1. Write GSD's CLAUDE.md to `.planning/_intake/gsd-claude-md-draft.md` temporarily.
2. Read the existing CLAUDE.md.
3. Identify only additions in GSD's version that are not already covered.
4. Append those to the END of the existing CLAUDE.md marked with
   `<!-- GSD: added by gsd-core setup -->`.
5. Never touch, reorder, or rewrite existing content. Additions only.
6. Keep the final CLAUDE.md under 250 lines (hackathon context -- keep it scannable).
7. Delete the draft file.

GSD's roadmap is approved. Fill governance docs from GSD's `.planning/` artifacts.

**Token discipline -- three rules apply to this entire phase:**
- Read each `.planning/` file exactly once. Extract only the fields listed in the

- Do not re-summarise or re-describe anything GSD already wrote. Where HANDOFF.md or

- Do not re-ask any question GSD already asked or re-derive any decision GSD already made.
  If a field is in `.planning/PROJECT.md` or `.planning/ROADMAP.md`, use it verbatim.

**Read all sourcing files once at the start of Phase 3, before Step 1.**

Sourcing map:

| Doc | Section | Source |
|-----|---------|--------|
| AGENTS.md | Identity (framework, styling, deployment) | `.planning/research/STACK.md` |
| AGENTS.md | Task Queue | `.planning/ROADMAP.md` -- see translation rules below |
| AGENTS.md | Components | `.planning/ROADMAP.md` (initial list, expand as built) |
| AGENTS.md | Design Tokens | Phase 1 brief (LOCKED brand assets, or OPEN placeholder) |
| AGENTS.md | Team & Agents | Phase 1 extraction + team input |
| CLAUDE.md | Merge from GSD | Phase 2 Step 2 merge protocol |

| HANDOFF.md | Standing blockers | LOW-confidence items + any infra setup still needed |
| HANDOFF.md | Session 1 log | Date, problem statement summary, phase count, next task |

### Task Queue translation -- GSD roadmap -> V-prefix format

GSD produces a roadmap with named phases and tasks. Before filling AGENTS.md,
translate GSD's structure into the V-prefix queue format:

```
GSD phase 0 (foundation/setup)  ->  T1
GSD phase 1 tasks (parallel)    ->  V1a, V1b, V1c (one letter per parallel task)
GSD phase 1 compositor          ->  V1d (depends on V1a, V1b, V1c)
GSD phase 2 tasks (parallel)    ->  V2a, V2b, ...
GSD final phase (deploy/QA)     ->  V3 (always last, always: polish + deploy + mobile QA + demo prep)
```

Rules for the translation:
- Every GSD task that is independently buildable with no file overlap from another
  becomes a separate V-prefix row with a letter suffix (V1a, V1b, etc.).
- Every GSD task that wires together the above becomes a compositor row (V1d).
- GSD's deploy/QA/demo phase always maps to V3, never to V2x.
- Dependency chains must be explicit: V1d depends on V1a, V1b, V1c -- not on V1.
- Status: T1 = available, all others = blocked (scripts unblock automatically).
- Claimed By: leave blank for all rows.

After translation, verify: at least 2 V1x tasks are simultaneously claimable after T1.
If only one V1 task is claimable at a time, go back and split it.

### Step 1 -- Fill AGENTS.md

## MULTI-AGENT RESUME CONTRACT

With 3 parallel builders, HANDOFF.md Quick resume uses last-writer-wins. If each person
writes their personal task state there, teammates' context gets stomped on every push.
This contract prevents that by splitting resume context into three layers, each owned
by a different source:

### Layer 1 -- Project state (Quick resume in HANDOFF.md)

Quick resume is PROJECT-LEVEL ONLY. It answers: "Where is the overall project right now?"
Not: "What was I personally doing?"

Ownership: the person who most recently completed a V-prefix task updates this sentence.
Format: "[Time]. [What milestone was just reached]. [What the team is working on now]."
Example: "Day 1 14:30. V1 done -- claimant flow demoable. Team on V2a/V2b/V3."

Do NOT write personal task state into Quick resume. Do NOT write "I was halfway through
the modal" -- that belongs in the Session log.

### Layer 2 -- Personal task context (AGENTS.md Claimed By + Session log)

A resuming session finds its own personal context in two places:

1. **AGENTS.md Claimed By column**: shows exactly which task has your name on it right now.
   Run `bash scripts/next-task.sh` -- your in-progress task shows under IN PROGRESS with
   your name. That tells you exactly where to resume without reading anything else.

2. **Session log (HANDOFF.md)**: append-only, never overwritten. Find your most recent row.
   That row holds the last thing you committed and any mid-task notes you left.
   Format: `| [session #] | [date/time] | [owner] | [what was done / where I stopped] |`

Ownership: each person appends their own row. Never overwrite a teammate's row.

### Layer 3 -- Project blockers (Standing blockers in HANDOFF.md)

Standing blockers are team-wide. Any person adds a blocker. Any person removes it
(by striking it or deleting it) when it is resolved. No single owner.

### Resume sequence for any session (3-person team)

When `print-handoff.sh` runs on session start, read the output in this order:

1. Quick resume -> overall project state in one sentence
2. Current state -> feature freeze countdown, what phase the project is in
3. Standing blockers -> anything blocking the whole team
4. YOUR personal context:
   a. Run `bash scripts/next-task.sh` -> find your name under IN PROGRESS
   b. If your name is there: resume that task. Read your most recent Session log row.
   c. If your name is NOT there: you have no claimed task. Run next-task.sh output
      shows CLAIMABLE NOW -- pick one and claim it.

This sequence works identically for all 3 people simultaneously. No stomping.
No one reads another person's personal context. The queue is always the ground truth.

### Session log column format (update from Phase 3 onward)

Change the Session log table in HANDOFF.md to include an Owner column:

```
| # | Date/Time | Owner | Summary |
|---|---|---|---|
| 1 | Day 1 09:00 | lead       | Planning session. GSD roadmap approved. |
| 2 | Day 1 10:45 | teammate-A | Claimed V1a. AppShell + router wired. |
| 3 | Day 1 10:50 | teammate-B | Claimed V1b. Mock data + primary card done. |
```

The Owner column is what lets a resuming session scan the log for their own rows only.
Replace teammate-A and teammate-B with actual GitHub usernames on Day 1.

## PITCH PHASE

Pitch is a first-class phase, not an afterthought. Every project carries three pitch tasks
in the AGENTS.md queue, claimable only after feature freeze:

- P1: pitch script + click-path demo script
- P2: slide deck built in the product's own design language (HTML deck using
  design-system tokens), so pitch and product read as one designed thing
- P3: rehearsal + backup capture

Full protocol: `docs/pitch-playbook.md`. The deck reuses `design-system/README.md` tokens
(same fonts, colours, spacing, components as the product); judges register that coherence as
polish.

## LIVE DOCUMENTATION HOOKS (hackathon-adapted)

These hooks are lighter than the full client project version. Run them after every
completed feature, not just end of session. In a 48-hour sprint, context loss is fatal.

Hook 1 -- After any new route or screen is completed:
Update AGENTS.md Pages & Routes table (route, component, owner, status).

Hook 2 -- After any new component is created:
Update AGENTS.md Components table (name, file, owner, status).

Hook 3 -- After any scope change (feature added, cut, or deferred):
Update HANDOFF.md Scope changes log (what changed, why, who decided).

Hook 4 -- After every work block (not just end of session):
Update HANDOFF.md: Quick resume (project-level only, overwrite) + Current state
(overwrite) + append your own Session log row (Owner column, never overwrite others).
Set HANDOFF_SYNCED_COMMIT to HEAD, commit, push.
Stop hook blocks session close if this is skipped.

Hook 5 -- After any code failure (bug fixed or approach abandoned):
Add a permanent entry to HANDOFF.md Code failures & fixes. Never prune this.
In a hackathon, repeating a failed approach kills hours.

Hook 6 -- After UI polish session (Day 2, after feature freeze):
Update AGENTS.md Design Tokens table with agreed token values.
Update design-system/README.md.
Every teammate's agent reads from this -- never leave it as [fill after Rule 0].

Summary: AGENTS.md and HANDOFF.md must always reflect the current true state.
Stale docs in a 48-hour sprint are as bad as no docs.

## RESUMING MID-HACKATHON

If a new Claude session opens mid-hackathon (device switch, context limit, etc.):

1. `scripts/print-handoff.sh` auto-runs via SessionStart hook and prints Quick resume
   (project state) + Current state + all Standing blockers (no cap).
2. Read CLAUDE.md (always read on session start).
3. Find YOUR personal task context using the resume sequence in MULTI-AGENT RESUME
   CONTRACT above: run `next-task.sh`, find your name in IN PROGRESS, read your most
   recent Session log row (Owner column).
4. If `.planning/ROADMAP.md` exists and HANDOFF.md shows a current phase: run
   `/gsd-resume` or `/gsd-plan-phase [N]` for the current phase. Do not re-run
   this skill from Phase 1.
5. Pull latest before writing a single line of code.

The repo is the brain. Trust the repo, not session memory.

## RESEARCH FRESHNESS

GSD re-researches stack, UX patterns, and pitfalls fresh on every `/gsd-new-project`
invocation. The one residual risk is any supplementary search this skill runs (e.g.,
verifying a library version or checking if a Vite plugin exists). Apply the same rule:
never reuse package names or versions from memory -- always verify live. Using an
outdated or renamed package mid-sprint wastes hours you do not have.
